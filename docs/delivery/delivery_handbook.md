## 这份合集是什么

它是一份**入口**：把一个真实交付项目的五份文档串成一条线，让你知道**先读哪份、每份回答什么问题、哪些数字是算出来的**。

五份文档按交付顺序排列，每份解决客户心里的一个疑问 —— 从「该做什么」到「凭什么信你」，再到「二期铺多大、按什么节奏」。

**一句话：13 个环节建议投入、2 个明确劝退、合计年省 1624 小时 —— 每一步都有可核对的依据。**

## 交付顺序：五个问题，一条线

客户不会按你想的顺序读文档。真实顺序是**跟着他的疑问走**：

1. **先做哪个** → [`discovery_report.md`](discovery_report.md)　_客户业务负责人_
2. **怎么做** → [`solution_blueprint.md`](solution_blueprint.md)　_客户业务 + 技术双方（可签字）_
3. **凭什么信你** → [`case_backtest.md`](case_backtest.md)　_客户技术评审 / 采购_
4. **能复制到哪** → [`expansion_matrix.md`](expansion_matrix.md)　_客户管理层（决定二期范围）_
5. **按什么节奏铺** → [`rollout_calendar.md`](rollout_calendar.md)　_客户项目负责人（排期与里程碑）_

顺序不能换。先说「怎么做」客户会问「凭什么做这个」，先说「能铺多大」客户会问「单点跑不跑得通」。**这条顺序本身就是交付方法的一部分。**

## 哪些数字是算出来的，哪些不是

这是整份手册最该被先读懂的一节 —— **任何咨询交付都该经得起「你这个数哪来的」这一问。**

| 数字 | 来源 | 性质 |
|---|---|---|
| 评估环节 15 个 / 建议投入 13 个 | `diagnosis.py` 五维打分 | 🟢 实算 |
| 可落地年省 1624 小时 | diagnosis 的 `annual_hours_saved` 求和 | 🟢 实算 |
| 字段编码正确率 / 重试成功率 / 单表最大并发 | `make eval` 压测与故障注入 | 🟢 实算 |
| 飞书真实交互证据 | cassette 录制的真实租户请求 | 🟢 实测 |
| 「可复制到」的业务域 | 从已验证场景抽象的定性判断 | 🟡 定性 |
| 推广时间轴（T0 / 1-2 月 / 2-3 月 / 3-6 月） | 先稳后难的排期决策 | 🟡 规划 |

**实算的会随场景包改动自动重算，定性的明确标注。** 没有任何一个数字是手写进文档的。

## 这套方法不承诺什么

交付材料说清楚边界，比堆成功案例更能建立信任。这套打法有四条明确的局限：

- **有 2 个环节明确不做**：数据在别人系统里、或动作出错会外部可见（对外可见动作交给专业人士）。劝退项写进报告并给前置动作，是交付价值的一部分，不是失败
- **能力模式可复制，具体判据不可照搬**：如库存÷销量的阈值是当前类目的经验值，换类目要重新标定
- **AI 草拟强依赖数据源**：目标业务没有历史文本沉淀的环节，这套模式直接退回「诚实劝退」，不硬凑 AI
- **时间轴是规划不是承诺**：波次顺序是先稳后难的决策，实际排期取决于客户侧数据就位速度

更完整的局限清单见 [`limitations.md`](../limitations.md)。

## 这些文档怎么维护

五份文档 + 本合集页全部是**报告即代码**：内容由脚本从 `scenarios.yaml`、cassette、eval 实算生成，改数据源重跑即更新，不存在手写漂移。

```bash
python scripts/gen_discovery_report.py    # 第 1 步
python scripts/gen_solution_blueprint.py  # 第 2 步
python scripts/gen_case_backtest.py       # 第 3 步
python scripts/gen_expansion_matrix.py    # 第 4 步
python scripts/gen_rollout_calendar.py    # 第 5 步
python scripts/gen_delivery_handbook.py   # 本合集页（需前五份先生成）
```

`make verify` 会校验全部文档的交叉引用有效性 —— 五份文档任一缺失或改名，合集页的指针会立刻报错，不会静默失效。
