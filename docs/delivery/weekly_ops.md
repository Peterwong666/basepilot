# 上线后每周运营手册（Weekly Ops）

> 面向：上线后负责「让它持续被用起来」的运营/顾问。
> 配套：`docs/delivery/delivery_playbook.md`（5 步交付）、
> `docs/delivery/troubleshooting.md`（排障 SOP）。

**核心立场**：交付签字 ≠ 项目成功。FDE 项目的真实成功标准是
**「交付 8 周后客户还在自己用」**。这份手册管的就是签字之后的那 8 周。

---

## 为什么需要这份手册

多数 ToB 交付死在同一个地方：**上线那周热热闹闹，第三周开始没人打开，第八周彻底荒废。**
死因几乎不是技术问题，而是这三个没人盯：

1. **促活指标没人算**——「用起来了」是一种感觉，不是数字
2. **异常闭环没人追**——台账记了异常，但没人确认它被处理了
3. **下个场景没人挖**——第一个场景站稳后，不主动挖第二个，项目价值封顶

这份手册把这三件事变成**每周固定 1 小时的 checklist**，每件事都有可执行的命令。

---

## 每周节奏（固定 1 小时，建议周一上午）

### ① 看促活指标（20 分钟）

playbook 里定义的三个指标，用脚本算出来填进周报：

| 指标 | 定义 | 健康值 | 怎么算 |
|---|---|---|---|
| **采用率** | 本周新建记录的人 / 目标使用人数 | > 70% | 多维表格「最近修改人」筛选本周去重 |
| **台账覆盖率** | 有记录的 SKU / 应覆盖 SKU | > 90% | `search_records` 拉全量 ÷ 客户 ERP 导出数 |
| **SLA 逾期率** | 超期未闭环 / 总未闭环 | < 15% | 见下面「逾期扫描」 |

**台账覆盖率**可直接用本项目能力算（以客户 ERP 导出的 SKU 清单为分母）：

```bash
# 拉全量 SKU 计数（去重前），与客户 ERP 导出的 SKU 总数比对
python -c "
import asyncio, os
from dotenv import load_dotenv; load_dotenv()
from basepilot.client import BitableClient

async def main():
    async with BitableClient(os.environ['BASEPILOT_APP_ID'],
                             os.environ['BASEPILOT_APP_SECRET']) as c:
        items = await c.search_records('<APP>', '<库存表ID>', field_names=['SKU'])
        print(f'台账内 SKU 数：{len(items)}')

asyncio.run(main())
"
```

**逾期扫描**：在库存/广告/差评表里，凡是「处理状态」不是「已闭环」
且「发现时间」早于 N 天前的记录，就是逾期。用 search 的 filter 一次拉出：

```python
filter_ = {
    "conjunction": "and",
    "conditions": [
        {"field_name": "处理状态", "operator": "isNot", "value": ["已闭环"]},
        {"field_name": "发现时间", "operator": "isLess",
         "value": ["ExactDate", "<N天前的毫秒时间戳>"]},
    ],
}
```

> 📋 **Backlog**：把这三条固化成 `make adoption` 一键出周报
> （当前需要手动跑上面命令）。playbook 里已引用 `make adoption`，
> 实现后排进 D12。

### ② 追未闭环异常（25 分钟）

把逾期清单拉出来后，**逐条问三个问题**：

1. 这条异常**业务上还存在吗**？（SKU 已下架的异常不用追，直接关）
2. 有人**认领**了吗？（没有认领人的，当场 @ 业务负责人指派）
3. 卡在哪一步？（缺数据 / 缺权限 / 缺决策——分别走不同路径）

**这一步的本质不是技术，是项目管理**。工具只负责把逾期暴露出来，
追着人闭环是 FDE 上线后最重要的价值。

### ③ 挖下一个场景（15 分钟）

用 `diagnose_scenarios` 工具跑一遍客户新提的流程，
四象限图当场出，客户自己看到哪个场景值得做：

```
工具：diagnose_scenarios
入参：客户这周某条新抱怨（「我们 XX 也是人工对的」）
产出：可自动化指数 + 象限 + 年省工时
```

**D 象限（劝退）的场景要如实说「这个不值得做」**——
劝退一次错误的需求，比硬接一个做砸的需求，对信任的累积大得多。

## 周报模板（每周五发客户）

```markdown
## XX 项目 第 N 周运营周报（MM/DD - MM/DD）

### 促活指标
- 采用率：__%（健康值 >70%）
- 台账覆盖率：__%（健康值 >90%）
- SLA 逾期率：__%（健康值 <15%）

### 本周闭环
- 新增异常记录 __ 条，闭环 __ 条，闭环率 __%
- 典型案例：[挑 1 条有业务价值的，一句话讲清楚]

### 逾期未闭环（__ 条）
| 记录 | 逾期天数 | 认领人 | 卡点 | 下一步 |
|---|---|---|---|---|

### 下周计划
- [ ] 动作 1
```

## 8 周路线图（与 playbook 的步骤 4 对齐）

| 周 | 重点 | 达标判据 |
|---|---|---|
| 1 | 陪跑第一次完整闭环 | 客户 1 人独立走完 1 条 |
| 2-3 | 每天看采用率，掉队即上门 | 采用率不破 60% |
| 4 | 第一份促活周报 | SLA 逾期率 < 20% |
| 5-7 | 挖第二个场景并小步验证 | 第二个场景进 dry_run |
| 8 | 复盘：哪些用起来了、哪些没用、为什么 | 形成可复制案例 |

**第 8 周复盘要诚实**：没用的是哪个、为什么——这个答案
比「成功了」更有价值，它是下一个客户项目的输入。

---

## 红线（出现任一情况立即升级）

- 采用率连续 2 周 < 50%：项目有荒废风险，**当面找一号位**
- SLA 逾期率 > 40%：异常处理流程本身有问题，不是人的问题
- 客户提出「能不能导出到 Excel 我们自己管」：**这是弃用前兆**，必须当面沟通
