# 客户现场交付 Playbook（5 步法）

> 面向：在企业客户现场把它用起来，而不是「交付完就走」的顾问与工程师。
> 配套：`docs/delivery/client_training.md`（培训）、`docs/delivery/troubleshooting.md`（排障）、
> `docs/delivery/weekly_ops.md`（上线后运营）。

**核心立场**：交付的产物不只是「能跑的代码」，而是**客户团队能自己维护下去的能力**。
所以每一步都以「客户是否能自己继续」为验收标准。

---

## 步骤 0 ·交付前自查（半天）

**这一步不做，后面全都会返工。**

- [ ] 客户是否已开通飞书**付费版本**？免费版的多维表格行数与自动化次数有限制
- [ ] 是否有**超级管理员**配合？（建应用、授权多维表格都需要管理员）
- [ ] 数据源是否可导出？（本项目依赖 Seller Central / 广告后台 CSV，
      如果客户连 CSV 都导不出来，这个场景就是 D 象限，不该做）
- [ ] 业务负责人是否愿意参加第一次沟通会？**一号位不到场的项目成功率显著更低**

---

## 步骤 1 · 建自建应用（30 分钟）

**在飞书开放平台**（open.feishu.cn）→ 开发者后台 → 创建企业自建应用。

命名建议：`{公司简称}-{场景简称}-FDE`，例：`ACME-跨境运营台账-FDE`

### 权限申请（按最小权限原则）

| 权限 scope | 用途 | 是否必需 |
|---|---|---|
| `bitable:app` | 读写多维表格 | ✅ 必需 |
| `bitable:app:readonly` | 只读（若仅做巡检看板，可只申请这个） | ✅ 必需 |
| `drive:drive` / 素材上传相关 | 附件写入需要 `upload_all` | 视是否用附件字段 |
| `contact:user.base:readonly` | 人员字段需要解析用户 | 视是否指派负责人 |

> ⚠️ **权限粒度是分开的**：申请少了接口报无权限，申请多了审核变慢。
> **按最小必要原则先跑通，再逐步加。**

### 立即提交版本审核（异步！）

**改完权限必须点「创建版本」并由管理员审核发布**，否则 API 调用会返回 403。
这是最常见的「代码没错但跑不通」—— 权限审核是异步的，**第一天就要提交**。

---

## 步骤 2 · 多维表格授权（10 分钟）

**这一步 90% 的客户会卡住，且卡在同一个地方。**

```
打开目标多维表格
  → 右上角「···」
    → 「更多」
      → 「添加文档应用」
        → 搜索你的自建应用名
          → 设为「可管理」协作者
```

**注意**：只给「可阅读」权限的话，API 会返回 `1254302` / `1254304` 权限不足。

**验证**：

```bash
# 首次连通性验证：能否读到表结构
make live-smoke --step schema
```

## 步骤 3 · 建表 + 搭工作流（半天）

### 建表的字段顺序有讲究

**先建数据源字段，最后建公式字段。**

原因：公式字段（`type=20`）依赖其他字段，字段不存在时公式报错。
反过来建会反复返工。

本项目三张表的设计顺序（详见 `scenarios/`）：

```
表1 SKU 库存健康：文本/单选/数字 → 日期/人员 → 复选框/附件 → 关联 → 公式（可售天数）放最后
表2 广告异常跟进：文本 → 单选/多选 → 货币/百分比 → 日期/人员 → 复选框
表3 差评处理：文本 → 星级/进度 → 单选 → 日期/人员 → 附件 → 关联
```

### 索引列的硬约束

**一张表只能有一个索引列（首列），且其类型只能是**：
`文本(1) / 数字(2) / 日期(5) / 电话(13) / 超链接(15) / 公式(20) / 复选框(22)`

所以 SKU、评价 ID、广告活动名这类业务主键**必须用文本**，
不能用「自动编号」—— 自动编号（type 1005）不能做索引列。

### 搭工作流时的真实约束

| 约束 | 影响 | 应对 |
|---|---|---|
| **工作流与自动化共用每月运行次数额度** | 高频定时工作流会吃掉额度 | 上线前核算：`工作流数 × 触发频率 × 30天`；本项目 W1每天 1 条 + W5 每周 1 条，额度可控 |
| 「工作流」支持条件分支与循环，「自动化」不支持 | 复杂逻辑要用工作流，不能用自动化 | 有 if-else 分支需求的，一律用工作流 |
| 条件分支**支持多层嵌套** | 别怕嵌套，但要控制层数（≥3 层难维护） | 本项目 W1 用了 2 层 |
| 附件/图片类字段在消息卡片里的展示有限制 | 通知里带图可能失败 | 消息只带文本 + 记录链接 |
| webhook 触发需 IP 白名单（≤10 个）+ Bearer token | 开发机没公网 IP 时配不了 | 本期不用 webhook，改用「定时触发 + 发送 HTTP 请求」 |

**最后一条是本项目的技术判断**（见 ADR-006）：
JD 里没有要求 webhook，且原生工作流已能覆盖定时同步场景且**零运维负担**。
真要用 webhook 时，先确认三件事：有没有公网 IPv4、能否接受 3 秒处理时限、
是否愿意维护 IP 白名单。

## 步骤 4 · 首次体检与冒烟（30 分钟）

```bash
# 全链路：体检 → 建表 → 写 → 查 → 更新 → 删
make live-smoke
```

**`bitable_doctor` 是客户现场最有用的工具**，它一次给出：

- token 是否有效、剩余多少秒
- app_token 是否可达、表清单、字段清单
- **哪些字段会被 coerce 拒绝**（公式/系统字段）
- 三个限流桶当前占用、各表写队列长度、最近错误码分布

客户现场最贵的不是写代码，是「不知道下一步干什么」。这个工具就是为此存在。

**验收标准**：`live-smoke` 全绿。**跑不通就是没交付**，不要口头宣布完成。

## 步骤 5 · 培训与陪跑（决定项目成败）

**交付完成 ≠ 项目成功。** 客户团队不用起来，前面 4 步全部白做。

### 上线当天（30 分钟）

- 用业务场景讲，不用功能清单讲：**「你每天早上打开这张表，第一屏看到什么，该做什么动作」**
- 现场让客户同事**自己操作一遍**，不要你演示给他们看
- 留一页纸速查表（见 `docs/delivery/client_training.md`）

### 上线后 4 周节奏

| 时间 | 动作 | 目标 |
|---|---|---|
| 第 1 周 | 每天 15 分钟站会；看是否有人**建记录** | 采用率 > 60% |
| 第 2 周 | 处理卡点；把高频手工动作再加一个工作流 | 首次闭环记录出现 |
| 第 4 周 | 出促活周报；收集下一个场景候选 | SLA 逾期率 < 20% |
| 第 8 周 | 复盘：哪些用起来了、哪些没用、为什么 | 形成可复制案例 |

### 判断「用起来了」的三个指标

| 指标 | 定义 | 健康值 |
|---|---|---|
| **采用率** | 周活跃创建人 / 目标使用人数 | > 70% |
| **台账覆盖率** | 有记录的 SKU / 应覆盖 SKU | > 90% |
| **SLA 逾期率** | 超期未处理 / 总未闭环 | < 15% |

**这三个指标都能用 `make adoption` 算出来**，不需要人工统计。

## 交付清单（签字用）

- [ ] 自建应用已创建、权限已按最小权限申请、**版本已由管理员发布**
- [ ] 多维表格已「添加文档应用」并设为可管理
- [ ] 表结构建好（索引列合规、公式字段放最后）
- [ ] 工作流已配好并在**真实触发**验证过（不是只配了没跑）
- [ ] `make live-smoke` 全绿
- [ ] 客户团队已至少 1 人独立完成 1 条完整闭环
- [ ] 培训材料已交付，且**客户能自己查到**
- [ ] 促活指标已在跑（`make adoption`）
- [ ] 排障 SOP 已交付（`docs/delivery/troubleshooting.md`）

**最后一条提醒**：真出现按手册解决不了的问题，
官方兜底路径是「飞书开放平台文档 → 开发者社区提问 → 服务商支持」，
**如实告诉客户这条路径，比硬扛更能建立信任。**
