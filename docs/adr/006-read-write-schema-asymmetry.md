# ADR-006：字段适配必须是「读结构≠写结构」感知的一等能力

- **状态**：已接受
- **日期**：2026-10-18
- 相关：[ADR-001（自研 httpx）](001-self-built-httpx-client.md)、[ADR-005（为什么不封装官方 lark-mcp）](005-why-not-wrap-official-lark-mcp.md)
- 证据：`tests/cassettes/cross_border_upsert.jsonl`、`tests/test_cassette_replay.py`

## 背景

飞书多维表格 API 有一个**文档不会明说、纯 Mock 测不出来、只在真实租户才暴露**的行为：

**同一个字段，写入时和读回时的数据结构不一样。**

| 字段类型 | 写入时（request） | 读回时（response） |
|---|---|---|
| 文本 (type=1) | `"PET-BOWL-001"` 纯字符串 | `[{"type":"text","text":"PET-BOWL-001"}]` 富文本数组 |
| URL (type=15) | `"https://..."` 纯字符串 | `{"link":"...","text":"...","type":"url"}` 对象 |
| 单选 (type=3) | `"正常"` 纯字符串 | `"正常"` 纯字符串（这个碰巧一致） |

这个不对称在两个地方会咬人，都是**客户现场数据事故**级别：

### 事故一：写入被拒（1254060 TextFieldConvFail）

如果按官方文档「字段值格式」表格里读到的富文本数组结构去**写**，
飞书返回 `1254060 TextFieldConvFail`。
文档里的那张表描述的是**读回**结构，但没标注——第一次对接的人几乎必踩。

### 事故二：upsert 重复创建（更隐蔽，不报错）

`batch_upsert` 的核心逻辑是「按唯一键查已存在 → 命中走 update，未命中走 create」。
如果拿**读回**的富文本数组当 dict 键去比对**写入**的纯字符串：

- `TypeError: unhashable type: 'list'`（数组不可哈希，直接崩），或
- `str([{...}])` 得到 repr 字符串，与写入值**永远比对不上**
  → 「已存在」的记录被判为「不存在」→ **重复创建**
  → 跨境 ERP 每天同步一次，同一 SKU 在表里出现 N 次

第二种更危险：**不报错、不抛异常，数据悄悄翻倍**，客户月底对账才发现。

## 决策

把「读结构≠写结构」的感知做成**引擎层一等能力**，而不是散落在各调用方的防御性代码：

1. **`coerce.py` 双向对称**：
   - encode 方向（`coerce_*` 系列）：写入前的格式适配（已存在）
   - **decode 方向（`normalize_key()`，本次新增）**：读回值的归一化

2. **`normalize_key()` 的归一化规则**（每种规则对应一个真实踩坑）：
   - 富文本数组 → 拼接所有 text 段（**支持多段文本**，只取 `kv[0]` 会丢数据）
   - URL 对象 → 取 `text`（与写入的纯字符串 link 一致）
   - 数值整数去小数点（`95.0` → `"95"`，否则与写入的 `95` 比对不上）
   - bool → `"true"/"false"`（先于 int 判断：Python bool 是 int 子类）
   - 无法安全归一的复杂结构 → `""`（**宁可判不存在走 create，也不 `str(repr)` 误判**）

3. **键提取收进 `client.upsert_records()`**：调用方不需要知道「读结构≠写结构」
   这个坑存在。tools 层的 `batch_upsert` 变薄封装。

## 为什么必须在引擎层，不能在脚本/工具层打补丁

这个决定是踩出来的：第一版 `normalize_key` 写在 `scripts/seed_cross_border.py`
里解决脚本自己的问题。但这意味着：

- 每个调 `batch_upsert` 的地方都要自己记得做归一化（**记得**是最不可靠的工程实践）
- tools 层的 `batch_upsert` 自己还有一份**只取 `kv[0]`** 的内联键提取（会丢多段文本）
- 两份实现逻辑不一致，哪个是对的没人说得清

收进引擎层后：**这个坑在引擎里被根治一次，所有调用方自动免疫。**
这是 cassette 驱动开发的价值闭环——真实租户踩坑 → 不是就地打补丁 → 回灌引擎层 → 配离线回归测试。

## 验证方式（三层，全部可重放）

| 层 | 证据 | 锁什么 |
|---|---|---|
| 离线单测 | `tests/test_normalize_key.py`（17 个） | 12 种读回形态参数化 + 核心回归「读回富文本→update 绝不 create」 |
| cassette 重放 | `tests/test_cassette_replay.py` + `cross_border_upsert.jsonl` | 写入纯字符串 / 读回富文本数组 / upsert 幂等——**真实 API 的原始字节** |
| 真实租户 | `scripts/seed_cross_border.py` 三表连跑 | 第一次 3+2+2 新增，第二次 0 新增全更新 |

任何把 `coerce_text` 改回富文本数组、或删掉 `normalize_key` 的改动，
cassette 重放测试会立刻红——这是「CI 里会红的断言」，不是 README 里手写的承诺。

## 会被问到的问题与回答

**"这种坑看文档不就能避免吗？"**

> 「不能。官方文档的『字段值格式』表描述的是读回结构，但没标注——
> 这张表同时被『写入』和『读取』两个文档引用，写的是同一个结构。
> 我是按文档写的，被 1254060 拒了，做对照实验（裸 API 各传一次纯字符串/富文本数组）
> 才确认写入要的是纯字符串。这就是为什么要 cassette：
> **文档告诉你应该是什么样，cassette 告诉你实际是什么样。**」

**"normalize_key 返回空串的那些复杂结构，丢了怎么办？"**

> 「判为『不存在』走 create。这是保守方向：最坏结果是多建一条记录，
> 人能看出来、能合并；另一个方向（str(repr) 误判为已存在）是**漏更新**，
> 数据悄悄过期，没人知道。两害相权，选会暴露的那个。」

**"为什么不用 vcrpy 之类的现成 cassette 库？"**

> 「见 cassette.py 头注释：我要对请求体做断言级检查——
> 『写入时文本字段是不是纯字符串』这条断言要拿到请求体的原始 JSON。
> vcrpy 把交互封在黑盒里，拿请求体要绕一层。自研 50 行换完全透明度。」
