# ADR-001：自研 httpx 客户端而非官方 lark-oapi SDK

- **状态**：已接受
- **日期**：2026-10-18

## 背景

飞书开放平台提供了官方 Python SDK `lark-oapi`，覆盖全部开放接口，内置了
token 缓存、重试、请求签名等能力。直接使用它是最省事的方案。

## 决策

**BasePilot 使用裸 `httpx` 自建客户端**，不使用 `lark-oapi`。

## 理由

### 1. 需要对关键指标做可断言的计数

本项目的核心可信度指标之一是「100 次业务请求 → 向飞书换 token 1 次」。
SDK 把 token 获取封装在内部，我**无法在测试里对 token 请求计数**，
也就无法写这条断言。

同理，「dry_run 模式下真实 HTTP 调用数必须为 0」这个指标，
需要对 HTTP 层有完全控制权才能验证。

自建客户端让这两条指标可测、可断言。这是 README 证据卡的数字来源，
必须可信，不能靠"我读了文档觉得会这样"。

### 2. 错误分类需要按业务语义重写

飞书的错误响应是统一的 `{code, msg}` 结构，但**处置策略是业务决策**：

| 错误码 | 官方 SDK 的行为 | BasePilot 的行为 |
|---|---|---|
| 1254291 写冲突 | 归为普通失败 | 退避重试 + 提示调大节流间隔 |
| 1255006 幂等键冲突 | 归为普通失败 | 重新生成 uuid4 后重试 |
| 1254302 权限不足 | 抛出原始错误 | 返回「添加文档应用」四步指引 |

把这些逻辑塞进 SDK 的重试框架会很别扭，且无法产出**面向客户的现场指引**。
而后者恰恰是 FDE 交付的核心价值。

### 3. 需要支持录制回放测试

录制回放要求按「HTTP 方法 + 路径模板 + body 关键字段」匹配 cassette，
未命中直接 fail。SDK 的多层封装会让这个匹配变得脆弱。

自建客户端只有一层 `httpx`，transport 层替换简单，replay 实现干净。

### 4. 依赖体量

`lark-oapi` 会引入大量生成代码与传递依赖。BasePilot 只需要 4 个直接依赖
（httpx / fastmcp / pydantic / pydantic-settings），对一个 MCP Server 来说更轻。

## 代价

- 需要自己维护 API 路径与请求体格式 —— 用配置常量集中管理（`config.py`）来控制。
- 无法享受 SDK 的自动重试 —— 但本项目本来就需要自定义退避策略（见 ADR-003）。
- 上游新增接口时需手动跟进 —— 但本项目定位明确，只覆盖多维表格域（见 non-goals）。

## 验证方式

`tests/test_auth.py::test_100_requests_fetch_token_once` —
断言 100 次业务请求后 `cache.fetch_count == 1`。若改用 SDK，此断言无法编写。
