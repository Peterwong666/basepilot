# ADR-003：单表写串行 + 节流，把 1254291 从「撞上重试」变成「主动规避」

- **状态**：已接受
- **日期**：2026-10-18
- 相关：[ADR-001（自研 httpx）](001-self-built-httpx-client.md)、[ADR-005（为什么不封装官方 lark-mcp）](005-why-not-wrap-official-lark-mcp.md)
- 证据：`src/basepilot/serialization.py`、`tests/test_serialization.py`、`eval/runner.py::_measure_max_inflight`

## 背景

飞书官方对写冲突的错误码说明里藏着两条**不在 API 文档正文、而在错误码排查建议里**的约束：

- `1254291`「Write conflict」排查建议原文：「若操作量较大，**建议在接口与接口之间
  增加 0.5 或 1 秒的延迟**」
- `1254607` 补充：底层「**基于版本维度的串行方式，不支持并发**」

翻译成工程语言：**同一张数据表，服务端不保证并发写的正确性**。
两条写请求同时打到同一张表，后到的可能覆盖先到的（版本冲突），或直接报 1254291。

这对「AI 批量灌数据」是致命的：LLM 发起 200 条 create 是并发的，
如果客户端不做任何控制，飞书侧会随机失败一部分——
**不是参数错了，是节奏错了**。

## 决策

把「同表不并发」从官方的一句排查建议，变成**客户端的运行时保证**：

1. **per-`table_id` 的锁**（不是全局锁）：
   同一张表的写请求串行；**不同表之间仍可并行**——
   客户同时写「库存表」和「广告表」不该互相等。

2. **0.5s 请求节流**：同一张表两次写之间至少间隔 `WRITE_MIN_INTERVAL` 秒。
   依据就是 1254291 排查建议的原文「0.5 或 1 秒」。

3. **可观测指标内建**：`inflight` / `max_inflight` / `throttle_wait_total` / `write_count`
   由 serializer 直接观测，压测可断言。

## 为什么不是「撞上了再重试」

| 方案 | 后果 |
|---|---|
| 不控制，撞上 1254291 再重试 | 每次冲突浪费一次配额 + 一次往返；200 条批量写入冲突率是统计性的，**无法承诺 SLA** |
| 全局锁（所有表串行） | 安全但慢——库存表写的时候广告表干等，客户不接受 |
| **per-table 锁 + 节流**（本方案） | 同表安全，异表并行；200 压测 `1254291` 计数 = 0 |

核心判断：**1254291 是「节奏错了」不是「参数错了」，重试不解决根因**。
撞上再重试是把成本转嫁给飞书配额和客户的等待时间；
主动节流是把成本变成可预测的 0.5s 间隔——后者才能写进 SLA。

## 验证方式（全部可复现）

| 层 | 证据 | 锁什么 |
|---|---|---|
| 压测 | `tests/test_client.py::test_same_table_writes_are_serialized` | 50 并发 → 飞书侧观测峰值 = 1 |
| 压测 | `tests/test_serialization.py`（5 个） | 200 并发压测 max_inflight=1、不同表并行、节流生效、指标计数 |
| eval | `eval/runner.py::_measure_max_inflight` | 证据卡「单表最大并发写 = 1」实算来源 |

## 会被问到的问题与回答

**"0.5s 节流会不会太慢？200 条要等 100 秒？"**

> 「会，但这是飞书的约束不是我的选择。官方排查建议写的就是 0.5-1 秒。
> 而且只在**同一张表**内节流——客户写库存表的同时写广告表是并行的。
> 真嫌慢的正确解法是把多条记录合进一次 batch_create（1000 条/次），
> 而不是取消节流去赌 1254291。」

**"为什么锁的粒度是 table_id 不是 app_token？"**

> 「一个多维表格 app 下有几十张表。锁 app 意味着写任何一张表都阻塞其它所有表，
> 客户同时维护库存表和广告表会互相等到不可用。
> 锁 table 是让「必要的串行」和「不必要的等待」分开——
> 这是从 1254607『基于版本维度』推断出来的：**版本是按表维度的，锁也该是**。」
