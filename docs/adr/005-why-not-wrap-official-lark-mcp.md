# ADR-005：为什么不封装官方 lark-mcp

- **状态**：已接受
- **日期**：2026-10-18
- 相关：[ADR-001（自研 httpx 而非官方 SDK）](001-self-built-httpx-client.md)

## 背景

飞书官方提供了 `@larksuiteoapi/lark-mcp`（npm 包），把开放平台 API 直接暴露为 MCP 工具。
覆盖度很广（40+ 工具，含 bitable、docs、im、calendar 等多个域）。

从工程角度看，封装它几乎总是更好的选择：维护成本低、上游更新自动跟随。
一个理性的人应该直接用它，而不是自己写。

所以这个 ADR 要回答的不是"我的方案更好"，而是**"在什么边界上不同，以及为什么这个边界值得付代价"**。

---

## 决策

**不复用官方 lark-mcp 的 bitable 工具集**，自建 MCP 工具层，
但**在同一进程内直接调用飞书多维表格本身**（工作流、自动化、表单等原生能力仍是飞书的）。

---

## 理由

### 理由一：可断言的交付可靠性（这是核心理由）

本项目的核心可信度指标是这几个数字：

| 指标 | 目标值 |
|---|---|
| 100 次业务请求 → 向飞书换 token 次数 | 1 |
| 200 次压测 → 单表最大并发写 | 1 |
| 200 次压测 → `1254291` 出现次数 | 0 |
| `dry_run` 模式 → 真实 HTTP 调用数 | 0 |

**这些数字用官方 SDK 写不出来。**

原因很具体：SDK 把 token 缓存与自动重试封装在内部，
我**无法在测试里对"换 token 请求"计数**，也无法统计"SDK 内部重试了几次"。
而这三层封装正是官方工具的价值所在 —— 也就是说，
**官方 SDK 做得好的部分（省心）和本项目要证明的部分（可验证）恰好冲突**。

自建 httpx 层意味着：请求发出前的每一层都由我控制，因此每一层都能被 mock 计数。
`tests/test_auth.py::test_100_requests_fetch_token_once` 这条断言，
在官方 SDK 下是无法编写的。

> 换个说法：**这不是重复造轮子，是为了让交付承诺从"我读了文档觉得会这样"
> 变成"CI 里会红的断言"。** 客户签的是承诺，不是工具。

### 理由二：官方工具不覆盖 FDE 真正要交付的那一半

把飞书 FDE 岗位的职责拆开看：

| JD 职责 | 官方 lark-mcp 能否支撑 |
|---|---|
| 客户诊断（判断哪个环节该上 AI） | ❌ 无 |
| 多维表格读写 | ✅ 能 |
| **原生工作流 / 自动化编排** | ❌ **无对应开放 API** |
| **交付陪跑与促活度量** | ❌ 无 |
| 方案书 / 培训手册 / 排障 SOP | ❌ 无 |

**关键事实**：JD 里写的「熟练使用飞书多维表格、**低代码平台**快速落地业务自动化」，
"低代码平台"指的是飞书**原生的工作流 / 自动化引擎** —— 条件分支（多层嵌套）、
AI 生成文本节点、定时触发、每月额度管理。

这些能力**在飞书服务器内部执行，没有对应的开放 API**，
只能在飞书界面里配置。官方 lark-mcp 走的是 open API 层，天然覆盖不到。

所以本项目是**把 API 层与原生低代码层缝在一起的那个交付包**。
缝合处正是 `coerce.py`：它被三个入口共享（见 ADR-004），
消除「多条写入路径各自实现一遍字段适配」的经典交付事故。

### 理由三：错误处置是业务决策，不是库能替我做的

飞书返回统一的 `{code, msg}`，但**处置策略是业务判断**：

| 错误码 | 通用库的典型做法 | 本项目的做法 |
|---|---|---|
| `1254291` 写冲突 | 归为普通失败 | 退避重试 + 提示调大节流间隔 |
| `1255006` 幂等键冲突 | 归为普通失败 | 重新生成 uuid4 后重试 |
| `1254036` 副本复制中 | 退避重试 | **长退避**（3s/6s/12s，上限 5 次） |
| `1254302` 权限不足 | 抛出原始错误 | 返回「···」→「更多」→「添加文档应用」四步指引 |

最后一条是关键：**FDE 交付的产物不只是"能跑的代码"，还有"客户现场照着就能做的指引"。**
把这 32 条处置规则连同现场动作沉淀下来，是这个项目区别于"能读写的工具"的地方。

## 代价（诚实列出）

| 代价 | 严重度 | 缓解 |
|---|---|---|
| **覆盖度远不如官方**（11 个工具 vs 40+） | 高 | **不与官方争覆盖度**。明确 non-goals：不做 docs / im / calendar / approval / 任务 |
| 上游新增接口需手动跟进 | 中 | 定位明确，只做多维表格域；新增接口时补一个编码器 + 黄金用例即可 |
| 多了一层需自己维护的代码 | 中 | 32 条错误码规则有表驱动测试全覆盖；`docs/delivery/troubleshooting.md` 由代码自动生成，不会与实现脱节 |
| 可能与官方 SDK 的边界判断有误 | 低 | 已写进 README 对比表，若判断有误可随时切换 —— 这也是选裸 httpx 而非深度绑定 SDK 的好处 |

## 会被问到的问题与回答

**"官方 lark-mcp 已经有了，你为什么重复造？"**

> 「这个问题问得很对，我先说结论：**如果只是要读写多维表格，官方 lark-mcp 一定比我选**，
> 它的工具覆盖面更广，我不该重复造。
>
> 我做这个项目是两个客户会付钱的理由：
>
> **第一，可断言的交付可靠性。** 我要能证明「100 次业务请求只换 1 次 token」
> 「200 次压测单表并发写峰值=1、1254291 出现 0 次」「dry-run 真实调用数为 0」。
> 这些数字用官方 SDK **写不出来** —— 它把 token 缓存和重试封在内部，我没法 mock 计数。
> 我自建 httpx 层就是为了让这些承诺变成 CI 里会红的断言，而不是 README 里手写的数字。
>
> **第二，覆盖 lark-mcp 不覆盖的那一半。** lark-mcp 走 API 层，但 JD 里写的
> 『低代码平台快速落地业务自动化』指的是飞书**原生工作流 / 自动化** ——
> 条件分支、AI 生成文本节点、每月额度管理，**这些根本没有对应的开放 API**，
> 只能在飞书界面里配。
>
> 我确实用了官方的东西 —— 多维表格本身是飞书的，工作流是飞书原生的，
> 我只补了官方工具**故意不覆盖**的那一段。」

---

## 验证方式

- README 首屏放**三列对比表**（官方 lark-mcp / 社区 bitable-mcp / 本项目），逐行有依据
- 现场跑 `make verify`，30 秒全绿 —— 证明断言真的存在且通过
- `tests/test_auth.py` 中 `test_100_requests_fetch_token_once` 存在且通过，
  这是"可断言"这一主张的直接证据
