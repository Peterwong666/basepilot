## 一、项目一句话

**BasePilot 是一个飞书多维表格 MCP Server**：把「判断哪些业务环节值得上 AI」的诊断方法，
落到「在真实飞书租户建好三张跨境电商运营台账并跑通」的工程交付，
再用一整套「报告即代码」的文档把方法论固化成可复制资产。

它要证明的不是「我会调 API」，而是 **FDE（前置部署工程师）的完整闭环**：
诊断 → 交付 → 回测 → 复制 → 推广。

## 三、结构分析：项目是怎么分层的

整个项目按「**引擎五层 + 三条横切线**」组织。理解这个骨架，就看懂了所有文件为什么在这些位置。

### 3.1 引擎五层（自下而上，每层可独立测试）

```
┌─────────────────────────────────────────────┐
│ L5  MCP 工具层   tools/      8 个工具给 AI 用  │
├─────────────────────────────────────────────┤
│ L4  client      client.py   裸 httpx 串调用链 │
├─────────────────────────────────────────────┤
│ L3  serialization  单表写串行 + 0.5s 节流      │
├─────────────────────────────────────────────┤
│ L2  schema + coerce  字段类型适配（读写两套）   │
├─────────────────────────────────────────────┤
│ L1  config/auth/errors/ratelimit  可信度地基   │
└─────────────────────────────────────────────┘
```

**为什么这样分**：每一层只对一个真实踩过的坑负责。
L2 管「读结构≠写结构」，L3 管「同表并发写 1254291」，L1 管「token 刷新/限流」。
坑是分层暴露的，所以代码也分层收口——**一层一个防御阵地**。

### 3.2 三条横切线（贯穿五层）

| 横切线 | 管什么 | 对应资产 |
|---|---|---|
| **诊断线** | 哪些环节值得做（业务判断） | `diagnosis.py` + `scenarios.yaml` + 五连报告 |
| **证据线** | 怎么证明真的跑过（可信度） | cassette + eval + live_smoke |
| **交付线** | 客户怎么用起来（方法论） | delivery 九篇文档 + ADR |

这三条线不是后加的包装，而是从第一个 commit 就和代码一起长出来的——
**代码答「能不能跑」，三条线答「该不该做 / 信不信得过 / 用不用得起」**。

## 四、主要节点复盘（问题 → 分析 → 解决）

按时间线排列，每个节点都是一次真实暴露的问题。这是本文档的核心。

### 节点 1：从「四维打分」到「五维打分」—— 指标逼出来的维度

- **问题**：初版诊断打分器只有 JD 原文的四维（高频/重复/耗人/有数据）。
  用秩相关检验自测时发现错位：**客服工单分类**年省 213h（最高）人工却只排第 9，
  **断货预警**年省 122h 人工却排第 2。模型排序和业务直觉对不上。
- **分析**：省工时 ≠ 值得做。断货在跨境业务里意味着 Listing 权重下滑 + 广告费白烧，
  一次损失数万元；工单分类省的只是键盘操作。「省时间」和「避损失」是两回事，
  而原模型**无法表达「不做的代价」**。
- **解决**：补第五维 `loss_impact`（不做的代价，权重 0.20）。
  秩相关从 0.533 提升到 0.650，残余错位如实标注在测试里。
  **这不是凑指标，是让模型能表达一个真实业务事实：防损型环节的价值不体现在工时上。**
- **证据**：`src/basepilot/diagnosis.py`、`tests/test_diagnosis.py`（秩相关回归测试）。

### 节点 2：cassette 实测发现「文本字段写入」的真 bug

- **问题**：`coerce_text` 把文本包成富文本数组 `[{"type":"text","text":...}]`，
  连真实飞书时 `batch_create` 报 `1254060 TextFieldConvFail`。
  **纯 Mock 测试根本测不出**——Mock 里喂什么返回什么。
- **分析**：对照实验（裸 API 各传一次）证实一个反直觉事实：
  **写入要纯字符串，读取才返回富文本数组**。「读结构 ≠ 写结构」。
  文档不会告诉你这个，只有真实租户踩了才知道。
- **解决**：修 `coerce_text` 写入侧为纯字符串 + 同步改黄金用例 + eval。
  错误码表沉淀 `1254060`（指引：写入纯字符串，富文本是读取结构）。
- **证据**：commit `a0bd4ce`、`docs/limitations.md`。

### 节点 3：upsert 静默重复创建 —— 比报错更危险的事故

- **问题**：`batch_upsert` 第二次跑，本应「存在即更新」却**重复创建了新记录**，
  且不报任何错——数据悄悄翻倍，客户月底对账才发现。
- **分析**：唯一键提取直接拿**读回**的富文本数组当 dict 键，
  触发 `TypeError: unhashable type: 'list'`；即便不炸，读回结构 ≠ 写入结构，
  键永远匹配不上 → 误判「不存在」→ 走 create。这是节点 2 的「 deeper 版」。
- **解决**：把 `normalize_key()` 提升为引擎一等能力（不放脚本侧打补丁）：
  富文本数组 → 拼 text 段；URL 对象 → text；数值整数去小数点；复杂结构 → ""（宁缺毋滥）。
  `client.upsert_records()` 统一返回 `{created, updated, skipped}`。
  17 个离线测试 + 真实租户回归（三表第二次跑 0 新增/全更新）。
- **证据**：commit `6c940e4`、`tests/test_normalize_key.py`、ADR-006。
- **教训**：**真实租户踩的坑必须回灌引擎层**，只在脚本侧打补丁，下次换个脚本又踩一遍。

### 节点 4：并发写撞 1254291 —— 「节奏错了」不是「参数错了」

- **问题**：同一张表并发写，飞书报 `1254291`。直觉反应是「加重试」。
- **分析**：1254291 是**并发节奏**问题，不是参数错误——重试只是换个时间再撞。
  关键依据是 `1254607`「版本维度串行」：飞书的版本是按表维度管理的，
  那写锁也该按表维度，而不是全局锁（全局锁会拖垮不同表的并行吞吐）。
- **解决**：`serialization.py` 做 per-table_id 锁 + 0.5s 节流，
  把「撞上再重试」改成「主动规避」。压测断言：同表并发写峰值=1、不同表可并行、失败释放锁。
- **证据**：commit `bf36c98`、ADR-003、eval「单表最大并发写=1」（200 并发压测实测）。

### 节点 5：四个写入口要共享一个编码器 —— 单一事实源

- **问题**：`create / update / upsert / dry_run` 是四个写入口，
  如果各自实现编码，会出现「同一条记录走不同入口得到不同结果」。
- **分析**：`dry_run` 的全部价值在于「预演 = 真实」。
  一旦编码器有两份，预演就失去了预测力——dry_run 说能过，真实写却报错。
- **解决**：`coerce.py` 作为唯一编码器，四个入口共享。
  `normalize_key` 也住在这里，因为 **encode（写）和 decode（读）是同一个事实的两个方向**。
  grep 实测四处调用分布，验证只有一份实现。
- **证据**：ADR-004、eval「dry-run 预测与真实返回码一致率 100%」。

### 节点 6：README 进度表说「建设中」，代码却已完成 —— 反向失信

- **问题**：eval 三个指标点亮后，发现 README 进度表还停留在骨架期：
  「建设中」「32 规则」「6 工具」「不能连真实飞书」。
- **分析**：README 是面试官第一眼看的东西。
  进度表说「建设中」而代码已完成，等于**第一眼就给人留下「说的和做的不一致」的印象**——
  这比 eval 指标没点亮更伤。
- **解决**：把进度表更新到真实状态（34 规则 / 8 工具 / 已三表幂等验证），
  并加 `check_doc_links.py` CI 门禁：README 引用的路径必须存在，
  预告但未做的进显式白名单，完成后必须移出。
- **证据**：commit `a948f2f`、`scripts/check_doc_links.py`。
- **教训**：**README 是最容易被遗忘更新的文件**，需要 CI 强制它说真话。

### 节点 7：fallback 清单缺第五维 —— 降级路径没人测

- **问题**：修蓝图脚本时误用全局 Python（无 PyYAML），触发 loader 降级到
  `_fallback_scenarios()`，结果 validate 报「缺少维度 loss_impact」——
  任何无 PyYAML 环境跑 `make diagnose` 都会崩。
- **分析**：`loss_impact` 是节点 1 后补的维度，但 fallback 清单没跟着加。
  主路径（有 PyYAML 读 yaml）一直正常，**降级路径成了没人走的暗角**，
  违背了 fallback「缺依赖也不瘫」的设计初衷。
- **解决**：fallback 四条场景补齐 `loss_impact` 并与 yaml 取值对齐；
  加两个回归测试（fallback 过 validate / fallback 与 yaml 打分不漂移）；
  实测 `yaml=None` 端到端 diagnose 通过。
- **证据**：commit `5fa79ac`、`tests/test_diagnosis.py`。
- **教训**：**降级路径也要进 CI**，否则「兜底」本身会变成新的故障点。

### 节点 8：交付文档「报告即代码」—— 让文档零漂移

- **问题**：FDE 要交五份文档（诊断/方案/回测/矩阵/日历）。
  手写的报告会过期——场景一改，数字就对不上。
- **分析**：文档里的数字（指数/年省工时/场景数/回测结果）都能从
  `diagnosis.py`、cassette、eval_report **算出来**。手写 = 必然漂移。
- **解决**：五份文档全部做成生成脚本（`gen_discovery_report.py` 等），数字实算不写死，
  配测试锁叙事结构（章节顺序 / 数字一致 / 无乱码 / 划分完备）。
  改源数据重跑即更新，文档永远和代码同频。
- **证据**：`scripts/gen_discovery_report.py`、`tests/test_discovery_report.py`、
  commit `66350d5`~`38ab067`。
- **关键叙事决策**：蓝图中 top3 全是 A 象限「不需要 AI」——这不是破绽，
  是优先级方法论的自洽输出（A 折算率 0.9 排前）。文档补「为什么没 AI」立场段，
  把疑点转成方法论证据。

## 五、FDE 交付方法论五连（对外讲解的主线）

五份「报告即代码」文档环环相扣，构成完整交付闭环。对外讲项目时按这个顺序：

| # | 文档 | 回答 | 一句话价值 |
|---|---|---|---|
| ① | `discovery_report.md` | 先做哪个 | 五维诊断 + 四象限，敢写 2 个劝退项 |
| ② | `solution_blueprint.md` | 怎么做 | top3 环节展开成技术/业务可签字方案 |
| ③ | `case_backtest.md` | 凭什么信你 | 真实证据回测当初预测，4/4 兑现 |
| ④ | `expansion_matrix.md` | 能复制到哪 | 15 场景归纳 4 种能力模式（合计 1624h/年） |
| ⑤ | `rollout_calendar.md` | 按什么节奏铺 | 4 波次先稳后难，劝退闸贯穿全程 |

**贯穿立场**：诚实劝退（D 象限）不是失败，是咨询底色——
敢在数据源没就位时说「先别做」，比多做一个勉强上线的场景更负责。

## 六、可复用的工程纪律（从坑里长出来的规则）

1. **真实租户驱动开发**：Mock 测不出「读结构≠写结构」这类坑，
   必须 cassette 录真实交互、CI 重放，让证据可复算。
2. **坑要回灌引擎层**：脚本侧打补丁 = 下次换脚本再踩一遍。
3. **报告即代码**：数字实算 + 测试锁结构，文档零漂移。
4. **README 说真话**：CI 门禁强制引用有效，白名单显式管理「预告未做」。
5. **降级路径进 CI**：fallback 也要有测试，否则兜底变故障点。
6. **每个指标都能答「是算的还是写的」**：eval 九项全实算，这是面试决定性追问的答案。
